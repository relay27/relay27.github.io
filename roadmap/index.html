KE—027 / 04 / 2027 ROADMAP

Build the boring
parts exceptionally well.

A provisional 2027 engineering roadmap. Each phase depends on evidence from the Toronto pilot, not a promised launch date.

Q12027 / PROPOSED

Instrument + stabilise

Establish baselines, log each transition and review failures. Add provider fallback drills and written operating procedures.

Exit gate: owners can trace a call and restore the original routing.

Q22027 / PROPOSED

Controlled integrations

Prototype calendar availability checks and draft work orders. Introduce isolated tenant settings, duplicate protection and permission-scoped adapters.

Exit gate: human-approved writes survive retries without duplicate bookings.

Q32027 / PROPOSED

Seasonal load + access

Exercise burst traffic, queue backpressure and backup notifications. Evaluate language support with real reviewers before enabling it.

Exit gate: load and accessibility tests meet agreed pilot criteria.

Q42027 / PROPOSED

Package + decide

Document deployment, retention, export and recovery. Explore an optional Raspberry Pi status display. Decide whether the evidence supports a broader beta.

Exit gate: publish a readiness decision, including limitations and costs.

01 / FIELD NOTES

Keep an honest engineering log.

Kostas brings an autotech technician’s troubleshooting habits to Raspberry Pi experiments and vibe coding. Generated code is a starting point: review, test and isolate it before connecting it to a customer-facing phone system.

Future updates should describe what changed, what was tested, what failed and what remains uncertain. Pilot company names and customer information stay out of public logs without permission.

02 / FIELD NOTES

A useful tool earns its place.

The next version should make the operator’s day easier without making the caller’s situation harder. If a feature creates more correction work than it removes, simplify it. If the pilot does not support expansion, keep the scope small.
